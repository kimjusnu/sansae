# 인트로 게이트 + 스크롤 스크럽 시퀀스 — 설계

작성일: 2026-07-28
대상: `portfolio/` (순수 HTML/CSS/JS, 빌드 없음, GitHub Pages 배포)

## 구현 상태 (2026-07-28)

전부 구현되어 있고 검증을 통과했다. 배경 영상은 `3.mp4`를 8초 전체, 192프레임으로 쓴다.

세 번의 렌더를 거쳐 결정했다.

| 렌더 | 밝기 | 파란 영역 | 판정 |
|---|---|---|---|
| 1.mp4 | 207 → 77 | 13% → 95% | 탈락. 좌측에 조명 장비가 찍히고 2.3초부터 화면이 파랑으로 덮임 |
| 2.mp4 | 174~178 | 19~25% | 탈락. 노출은 안정적이나 어두워 본문이 2.44:1까지 떨어지고, 4초 뒤 움직임이 멈춤 |
| **3.mp4** | **218~242** | **14~22%** | 채택. 8초 내내 밝기·움직임이 고르고 촬영 장비 없음 |

영상을 바꾸려면 `design/build-sequence.py`의 `SOURCE`와 `WINDOW`만 고치면 된다. 프레임 수는
매니페스트로 전달되므로 사이트 코드는 손대지 않는다.

### 인트로 노출 정책 변경

세션당 1회에서 **매 로드마다**로 바꿨다. 사용자 요청이며, 재방문자가 매번 게이트를 지나야 하는
비용을 감수한 선택이다. ESC 즉시 스킵, 딥링크 통과, reduced-motion 미표시는 그대로 유지된다.

버튼 문구는 `Deep Dive`이고, **버튼과 ESC만 입장시킨다.** 배경을 눌러도 들어가지 않는다. 다만
아무 반응 없는 클릭은 고장으로 읽히므로, 클릭 지점에 리플을 남기고 버튼을 한 번 튕겨 시선을 보낸다.

### 스크럽 끊김 해결

휠 한 노치는 약 110px을 움직인다. 고정 구간이 1,440px이므로 한 노치가 스크럽의 7.6%, 192프레임
기준 **약 15프레임을 한 번에 건너뛴다.** 프레임을 늘리는 것만으로는 해결되지 않는다 — 노치당 이동량은
스크롤 거리로 정해져 있기 때문이다.

두 가지로 풀었다.

1. **진행률 감쇠** — 스크롤 위치를 바로 쓰지 않고, 목표를 매 프레임 16%씩 따라가는 값으로 그린다.
   노치의 점프가 여러 애니메이션 프레임에 걸친 활강으로 바뀐다. 스크롤바보다 약간 뒤처지는데,
   그 지연이 부드러움의 정체다.
2. **프레임 사전 디코딩** — 도착 즉시 `img.decode()`를 호출한다. 활강 중 페인트가 디코딩을
   기다리지 않는다.

감쇠가 들어간 뒤에는 프레임을 늘리는 것이 실제로 효과가 있으므로 원본 192장을 전부 쓴다.

측정: 휠 6노치를 굴리며 애니메이션 프레임마다 그려진 진행률을 샘플링한 결과, 한 프레임 최대 이동이
**2.65프레임**(192분의)이고 149프레임 중 90프레임이 움직였다. 감쇠가 없으면 노치당 15프레임 점프다.

### 커스텀 커서

포인터 위치에 정확히 붙는 점과 뒤따라오는 링으로 구성한다. `(hover: hover) and (pointer: fine)`
에서만 동작하고, 터치 기기는 시스템 커서를 그대로 쓴다. 네이티브 커서는 커스텀 커서가 실제로
동작할 때만 숨긴다 — 이 모듈이 실패해도 포인터가 사라지는 일은 없어야 한다.

## 목적

첫 진입에 기억에 남는 순간을 만들되, 채용 담당자가 작업물에 도달하는 속도를 늦추지 않는다.

두 가지를 넣는다.

1. **인트로 게이트** — 버튼을 눌러 입장. 유리 큐브가 히어로 자리로 이동하며 페이지가 조립된다.
2. **스크롤 스크럽 시퀀스** — 히어로가 고정된 동안 배경 이미지 시퀀스가 스크롤에 맞춰 감긴다.

## 범위 밖

- 본문(원칙·강점·프로젝트·프로세스·경력·CTA) 레이아웃 변경
- 스크롤 하이재킹, 커스텀 스크롤 관성
- WebGL, 3D 라이브러리, 애니메이션 라이브러리 추가

## 1. 인트로 게이트

### 연출

동일한 큐브 DOM 노드가 인트로 중앙에서 히어로 우측 자리로 이동한다. 페이드아웃 후 다른 화면이 나오는 것이 아니라, 큐브가 도착하며 그 주위에 사이트가 조립된다.

| 시점 | 동작 |
|---|---|
| 진입 | 흰 화면 중앙에 큐브(최대 420px), 이름, `Deep Dive` 버튼. 뒤에 옅은 원근 그리드 |
| hover | 큐브 주변 궤도 링이 반응 |
| 클릭 +0.0~0.3s | 큐브에서 빛이 방사형으로 퍼짐. 그리드가 원근으로 물러남 |
| +0.2~0.9s | 큐브가 히어로 우측 자리로 이동. FLIP 착지 오차 0.0px |
| +0.4~1.0s | 헤더 하강. 배지 → h1 → 본문 → 버튼 → 메타 순으로 stagger 등장 |
| +1.0s | 인트로 DOM 제거 |

### 기술

- **FLIP** — 시작·끝 위치를 `getBoundingClientRect()`로 측정하고 `transform: translate() scale()`로만 보간한다. 레이아웃 재계산 없음, GPU 합성.
- 큐브는 기존 `icons/icon-hero-product-build.webp`를 재사용한다. 추가 에셋 없음.
- 그리드와 빛 확산은 CSS 그라디언트로 만든다.

### 게이트 정책

인트로가 매 방문마다 앞을 막으면 안 된다.

| 상황 | 동작 |
|---|---|
| 모든 로드 · 새로고침 | 인트로 표시 |
| `prefers-reduced-motion: reduce` | 인트로 없이 본문 |
| URL에 해시가 있는 진입 (`#work` 등) | 건너뜀 |
| ESC | 즉시 스킵 |
| 배경 클릭 | **입장하지 않음.** 리플 + 버튼 튕김 |
| JavaScript 비활성 | 인트로가 아예 표시되지 않고 본문은 정상 |

- `Deep Dive` 버튼은 실제 `<button>`이며 진입 시 자동 포커스된다.
- 인트로가 떠 있는 동안 배경 스크롤을 잠근다.
- 인트로 컨테이너는 `aria-hidden`이 아니라 실제 포커스 트랩으로 다룬다.

### 겸하는 역할

인트로가 떠 있는 1~2초 동안 스크럽 시퀀스의 저해상도 프레임을 미리 받는다. 장식이 아니라 프리로딩 창구다.

## 2. 스크롤 스크럽 시퀀스

### 방식 선택

`<video>`의 `currentTime`을 스크롤에 물리는 방식과 이미지 시퀀스를 Canvas에 그리는 방식을 검토했다.

`currentTime` 스크럽이 끊기는 원인은 키프레임 밀도다. 일반 H.264는 키프레임이 수 초마다 하나라서 임의 시점 seek이 직전 키프레임부터의 재디코딩을 강제한다. `-g 1`로 all-intra 인코딩하면 해결되지만 용량이 5~10배가 된다. 즉 제대로 하면 이미지 시퀀스와 비슷한 용량이 된다.

같은 값을 치른다면 프레임 정확도가 완전하고 iOS Safari에서 동작이 동일하며 점진적 로딩이 가능한 **이미지 시퀀스 + Canvas**를 택한다.

### 배치

별도 섹션을 끼우지 않고 **히어로 자체가 고정 구간**이 된다.

```
스크롤 0        히어로 고정 시작 · 프레임 0
   │            텍스트와 큐브 모두 선명
   │
   │            배경 시퀀스가 0 → 191로 감김
   │            텍스트가 위로 빠지며 투명해짐
   │
160vh 지난 뒤   고정 해제
   ↓
원칙 3칸 (흰 배경, 기존 그대로)
강점 · 프로젝트 · 프로세스 · 경력 · CTA
```

고정 구간의 스크롤 거리는 **뷰포트 높이의 1.6배**로 고정한다. sticky 래퍼의 높이는 `260vh`이고 그중 `100vh`가 화면에 붙어 있으므로 스크롤 가능 거리가 `160vh`가 된다. 뷰포트 높이 900px 기준 1,440px이며, 192프레임을 나누면 프레임당 약 7.5px이다.

`position: sticky`로 구현한다. 스크롤 이벤트를 가로채지 않으므로 스크롤바 위치가 정직하고 키보드 조작과 접근성이 유지된다.

### 스크롤 매핑

고정 구간 진행률 `p`(0→1)에 대해:

| 대상 | 0.0 | 1.0 | 비고 |
|---|---|---|---|
| 시퀀스 프레임 | 0 | 191 | 전 구간 선형 |
| 히어로 텍스트 `opacity` | 1 | 0 | `p = 0.5`에서 0 도달 |
| 히어로 텍스트 `translateY` | 0 | -40px | |
| 큐브 `scale` | 1 | 0.82 | |
| 큐브 `opacity` | 1 | 0 | `p = 0.8`에서 0 도달 |

큐브가 텍스트보다 늦게 사라진다. 시선의 앵커이기 때문이다.

### 렌더링

- `<canvas>` 하나에 `drawImage`로 현재 프레임만 그린다.
- 스크롤 위치를 직접 쓰지 않고, 목표를 매 프레임 16%씩 따라가는 감쇠 값으로 그린다.
- 프레임은 도착 즉시 `img.decode()`로 디코딩해 페인트가 멈추지 않게 한다.
- 목표에 도달하면 rAF 루프를 세운다. 리사이즈와 첫 페인트는 감쇠 없이 즉시 반영한다.
- 프레임 인덱스가 이전과 같으면 그리지 않는다.
- 캔버스 크기는 `devicePixelRatio`를 최대 2로 제한해 잡는다.
- 고정 구간을 벗어나면 캔버스를 `visibility: hidden`으로 두어 합성 비용을 없앤다.

### 로딩 전략

전체를 받을 때까지 기다리게 하지 않는다.

| 단계 | 내용 | 누적 |
|---|---|---|
| 1 | 포스터 1장 (프레임 0) | 13 KB |
| 2 | 10프레임 간격 20장 | 약 250 KB |
| 3 | 나머지 172장 백그라운드 수신 | 예산 내 |

2단계가 끝나면 이미 스크럽이 동작한다. 거칠지만 멈추지 않는다. 3단계는 도착하는 대로 채워 넣어 점점 부드러워진다. 아직 안 받은 프레임 자리에는 가장 가까운 수신 프레임을 그린다.

### 반응형과 대체 동작

| 조건 | 동작 |
|---|---|
| 뷰포트 ≥ 768px | 1024×576 세트 |
| 뷰포트 < 768px | 448×252 세트 |
| `prefers-reduced-motion: reduce` | 고정 구간 없음. 포스터 1장을 정적 배경으로 |
| `navigator.connection.saveData` | 위와 동일 |
| Canvas 미지원 또는 로딩 실패 | 위와 동일 |

어떤 경우에도 히어로 텍스트와 CTA는 정상 표시된다.

## 3. 에셋 사양

### 원본 (사용자 제공)

Ray3로 생성한다.

- 5~8초, 16:9, MP4 (채택본 `3.mp4`는 1280×720 · 8초 · 24fps)
- 카메라 거의 정지, 컷 전환 없음
- 처음부터 끝까지 **일정한 속도**. 스크럽은 속도 불균형을 그대로 드러낸다
- 화면의 70% 이상이 밝은 흰색. 위에 히어로 텍스트가 올라간다
- 파란 요소는 **화면 중앙 정사각형 영역 안에만**. 히어로(약 2.07:1)와 모바일 세로에 크롭되어 가장자리가 잘린다
- 글자·숫자·사람·로고 없음
- 루프 불필요 (스크럽이므로 첫 프레임과 끝 프레임이 이어지지 않아도 된다)

원본은 `design/sequence-source/`에 보존한다. 배포되지 않는다.

### 생성물

`design/build-sequence.py`가 ffmpeg으로 프레임을 추출하고 Pillow로 리사이즈·WebP 변환한다.

| 산출물 | 경로 | 사양 | 예산 |
|---|---|---|---|
| 데스크톱 세트 | `portfolio/sequence/hd/0000.webp` … `0191.webp` | 1024×576, 192장 | ≤ 2.6 MB |
| 모바일 세트 | `portfolio/sequence/sd/0000.webp` … `0191.webp` | 448×252, 192장 | ≤ 700 KB |
| 포스터 | `portfolio/sequence/poster.webp` | 1024×576 | ≤ 60 KB |

프레임 수 상한은 `MAX_FRAMES = 192`다. 원본이 그보다 길면 균등 샘플링해 줄인다.

WebP 품질은 예산을 맞추도록 스크립트가 조정한다. 시작값은 82, 하한은 55이며, 하한에서도 예산을 못 맞추면 경고를 출력한다.

### 용량 영향

계획값과 실측값 (3.mp4, 96프레임):

브라우저는 두 세트 중 하나만 받는다.

| | 이전 | 96프레임 | **192프레임 (현재)** |
|---|---|---|---|
| 데스크톱이 받는 양 | 186 KB | 1.17 MB | **2.35 MB** (q82) |
| 모바일이 받는 양 | 186 KB | 445 KB | **657 KB** (q70) |
| 저장소의 배포 폴더 | 564 KB | 2.8 MB | **4.3 MB** |

프레임을 두 배로 늘린 대가다. 128프레임으로 줄이면 데스크톱이 약 1.6 MB가 되고 부드러움은 조금
떨어진다. 예산을 넘기면 `build-sequence.py`가 WebP 품질을 자동으로 낮추고, 하한(q55)에서도 못
맞추면 조용히 넘어가지 않고 경고를 출력한다.

### 배경 위 텍스트 명암비

배경이 움직이므로 최악의 프레임 기준으로 재야 한다. 텍스트를 지운 상태로 렌더해 실제 배경만
측정했다 (데스크톱·모바일 × 진행률 0 / 0.3 / 0.6):

| 영역 | 데스크톱 | 모바일 | 기준 |
|---|---|---|---|
| H1 | 9.55:1 | 13.72:1 | 3:1 |
| 본문 lede | 7.71:1 | 12.12:1 | 4.5:1 |
| 메타 줄 | 5.58:1 | 5.58:1 | 4.5:1 |
| 배지 라벨 | 6.30:1 | 4.52:1 | 4.5:1 |

이를 위해 세 가지를 넣었다. 텍스트가 놓이는 쪽만 덮는 방향성 스크림(데스크톱은 좌→우, 모바일은
아래→위), 히어로 안에서만 적용되는 더 어두운 본문·메타 색, 그리고 불투명 배지 배경. 페이지 전체를
덮는 베일 대신 방향성 스크림을 쓴 이유는 큐브가 있는 쪽의 배경을 살리기 위해서다.

## 5. 검증 기준

기존 검증(정적 14항목, 기능 14항목, 320~1440px 오버플로 0)을 모두 통과한 상태를 유지하면서 다음을 추가한다.

**인트로**
- 첫 방문에 인트로가 뜨고, 새로고침하면 뜨지 않는다
- ESC로 스킵되고 포커스가 본문으로 이동한다
- `prefers-reduced-motion`에서 인트로가 뜨지 않는다
- `#work`로 직접 진입하면 인트로 없이 해당 섹션에 도달한다
- 인트로 종료 후 `document.body`에 스크롤 잠금이 남아 있지 않다

**시퀀스**
- 고정 구간에서 문서 `scrollWidth == clientWidth` (가로 오버플로 없음)
- 프레임 인덱스가 스크롤 진행률에 단조 증가한다
- 프레임을 하나도 못 받아도 히어로 텍스트와 CTA가 보인다
- `prefers-reduced-motion`에서 고정 구간이 생기지 않는다
- 스크롤 100회 왕복 시 콘솔 에러 0

**성능**
- 스크럽 중 롱태스크(50ms 초과) 0
- 데스크톱 세트 ≤ 2.2 MB, 모바일 세트 ≤ 600 KB

## 6. 구현 순서

1. `build-sequence.py` — 원본 없이도 동작 확인 가능하도록 더미 프레임 생성 모드 포함
2. 시퀀스 모듈 (로더 → 캔버스 → 스크롤 매핑 → 고정 구간)
3. 대체 동작 (reduced-motion, saveData, 로딩 실패)
4. 인트로 게이트 (정적 화면 → 게이트 정책 → FLIP 전환)
5. 인트로와 시퀀스 연결 (프리로딩)
6. 검증

원본 영상이 도착하기 전에 1~4를 더미 프레임으로 끝낸다. 영상이 오면 스크립트만 돌리면 된다.
