## 스토리 ① 브라우저 업데이트발 푸시 장애 — 홉 단위 진단과 3중 방어

- **상황**: 같은 코드가 Chrome은 정상, 특정 브라우저(버전 업데이트 후)만 웹푸시 미표시. "어제는 됐는데 오늘 안 된다."
- **행동**: OS 이벤트 로그로 푸시 파이프라인을 홉 단위 추적 → 네트워크·서버·OS 전부 성공, 브라우저 내부 마지막 홉에서 증발함을 실측 특정. 대안 가설 4개(채널 노후화·인코딩·OS 설정·자사 코드)를 각각 실험 설계해 전부 배제 — 제3자 사이트·타 origin으로 교차 검증까지.
- **해결**: 손댈 수 없는 계층이므로 **3중 방어 구조** 설계 — 푸시(즉시) + 폴링 폴백(안전망) + 탭 복귀 즉시 갱신. 브라우저가 패치되면 푸시가 자동으로 우선권을 되찾는 구조(코드 변경 불필요).
- **디테일**: 숨은 탭 타이머 스로틀링을 실측(5분 후 65초간 요청 0건)하고 Web Lock으로 면제 확보, tag 기반 중복 차단, 폴백-푸시 간 중복 방지 신호(postMessage).
- **교훈 문장**: "파이프라인 장애는 홉 단위로 갈라라", "'어제는 됐다'는 코드보다 환경을 먼저 의심하라"

## 스토리 ② 스펙이 백엔드보다 앞설 때 — feature-detection 전방호환

- **상황**: 백엔드 API 명세가 나왔지만 서버 구현이 일부만 존재. 모르는 필드를 보내면 422로 거부되는 스키마.
- **행동**: 실측으로 백엔드 현황을 기능별로 가르고, "새 프로토콜은 서버가 먼저 말할 때만 쓴다" 원칙의 감지 로직 구현.
- **결과**: 백엔드가 언제 배포되든 **프론트 재배포 0회**로 신기능 자동 활성. 양쪽 팀 배포 순서의 자유 확보.

## 스토리 ③ 파괴적 액션 보호 — 멱등키·낙관적 잠금

- 주문 문의: Idempotency-Key 발급, 선택 변경 시 재발급("다른 내용 = 다른 요청"), 409 시 자동 재전송 금지 — 사람에게 재시도를 돌려줌.
- 기준사진 변경: expected_version 낙관적 잠금 — 두 탭/두 사용자의 동시 수정 시 조용한 덮어쓰기 방지. 탭 2개로 실제 409 재현 검증.
- 기타 설계: 날짜는 문자열 앞 10자(KST 의도 보존), 미등록 status 원문 노출(전방 안전), 날짜별 lazy 렌더(수천 장 무프리즈, 91일치 실측), ESC 단계 소비, 접근성(role=dialog·포커스 복원).

## 검증·배포
