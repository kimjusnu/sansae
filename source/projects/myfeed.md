## ⚠️ 기술스택 — 정확 구분 (2026-08-06 프로젝트 저장소 확인)

- **마이피드 1.5 웹 (운영 중)**: FastAPI + Jinja2 SSR + jQuery/Bootstrap5(Metronic 테마) + vanilla JS 모듈 (페이지별 분리). 모니터링·모니터링 상세 2개 페이지만 ES Modules 구조 (브라우저 내 depth-anything-v2 추론 포함). Redis+Celery, MySQL, Chart.js, Service Worker+FCM, Nginx, S3+CloudFront.
- **회사 홈페이지(aimbelab.com)**: Next.js + TypeScript — **"Next.js 경험"은 이쪽으로 말할 것**
- 마이피드 1.0 = 별도 레거시(무관), 2.0 = 기획 단계(코드 없음), 앱 = Flutter(별도 저장소)
- ❌ 이력서·면접에서 "마이피드 = Next.js/React" 금지 — 프레임워크 없는 레거시를 모듈 구조로 다듬은 것이 오히려 강점 서사

## 규모·역할 (이력서 사용 가능 표현)

- **"전국 130여 농가·1,200여 사료빈을 모니터링하는 축산 IoT SaaS"** (고객사명 불요 표현으로 확인됨)
- 누적 센서 측정 레코드 수백만 건 + 촬영 이미지 수십만 건 규모
- 웹 개발 실질 2인 체제 — **본인 커밋 약 38% (355/941)**
- 단독(주도) 영역: 농장 모니터링 화면 전반 · admin(디바이스 모니터링·이미지 관리·알림 발송) · 사일로 프로파일 관리(POE) 화면 · 웹 알림 시스템 전체 · 성능·디자인시스템·i18n 정비 · 배포 절차 문서화

## 성능 개선 실측 수치 (커밋 기록 근거 — 자소서 사용 가능)

- 모니터링 상세 API 로드셀 매칭 **N+1 제거: 3개월 조회 기준 DB 왕복 약 2,400회 → 1회** (단일 배치 조회 + 이진탐색)

- 모니터링 목록 HTML 42% 경량화 (미사용 데이터 제거)
- 전 62개 화면 공통 로드 페이지당 139KB 절감 (미사용 스크립트 제거)
- 알림 미읽음 폴링 분당 6회 → 1회 + 숨은 탭 중단
- ❌ "페이지 로드 O초→O초" 단위 측정치는 기록에 없음 — 위 검증 가능한 수치만 사용

## AI 이미지 분류 성공률 90% → 97% (오류율 10% → 3%)

- **대상**: 사료빈(사일로) 상단에서 촬영한 이미지의 세그멘테이션/분류
- **경위**: 기존에 SAM(Segment Anything Model) 사용, 분류 성공률 약 90%.
  낮은 성공률이 답답해서 **본인이 직접 조사하다 SAM2 출시를 발견, 도입을 제안** → 적용 후 성공률 약 97%.
- **측정 방법**: 분류 실패(오분류) 이미지는 사람이 수동으로 구분하는 백업 시스템으로 넘어감.
  → **수동 처리로 넘어오는 이미지 비율**로 오류율을 측정. (10% → 3%)
- **자소서 포인트**: 시켜서 한 게 아니라 문제를 느끼고 스스로 대안을 찾아 제안·적용한 것.
  측정 근거(수동 검수 유입 비율)까지 말할 수 있음.

## 부패도 검증 AI (상세: 노션 "부패도 ai 설명")

- 부패를 단일 신호가 아닌 **누적 확률 문제로 재정의** (온습도 지속시간 × 사료 잔량 × 정체 시간)
- 이미지 위험(p_img) · 환경 위험(p_env) · 정체 위험(p_stag) 3개 확률을 독립 계산 후 가중 융합(p_fused)
- Yes/No가 아닌 확률 표현 + N회 연속 초과 시 경보 → 오탐 최소화
- 데이터 품질 저하 시 패널티 적용, 판단 근거를 사용자에게 설명 — 설명 가능한 AI 설계
